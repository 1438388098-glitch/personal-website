## The problem: wrong answers are what repay review; hoarding them is useless

Over time the wrong-answer book first became a warehouse: 1,655 wrong answers sat in the Zhuma backend, each recording only "you got this one wrong" — not even which option you had picked at the time was saved, let alone any synthesis of the knowledge points that kept recurring underneath the errors. Manual sorting is not sustainable: copying out, classifying and patching in error-prone and easily confused points for more than a thousand questions, one by one, could not be reviewed even once before the exam, and the enthusiasm for tidying rarely survives into a second round. So the goal was defined from the start as a repeatable pipeline: turn every wrong answer in the book into knowledge-point notes as printable, per-subject PDFs that can be recited directly, working back from wrong answers to the heavily tested points and filling in the error-prone and easily confused ones; apart from QR-code login and one learner-profile questionnaire, the whole run is orchestrated autonomously by the Agent with scripts and subagents, no manual intervention.

## Mechanism

The pipeline runs in five steps. Step one, full fetch: through Zhuma's internal read-only API — no submitting papers, no touching answer records — it pulls the question stems, the options, the correct answers and the complete official explanations, a density of information page scraping cannot reach; with resumable checkpoints, atomic writes and circuit-breaker backoff, an interrupted run is simply rerun. Step two, unit slicing: subjects are split further — a subject can hold 250+ questions, and is cut into units of at most 55 questions, handed to parallel subagents for separate processing. Step three, note generation: it first asks about the learner (weak subjects, review round, days to the exam, daily hours, habits, goals); notes are merged and deduplicated by knowledge point (not by question order), and each knowledge point is tagged "tested N times".

Step four, six-dimension review: once the notes are generated, multiple subagents review them in parallel along "subject × dimension" (statutory accuracy, answer consistency, coverage completeness, format compliance, learner fit, cross-unit cohesion), consolidated into a revision list; P0 issues must be revised and re-reviewed. The consolidation script carries its own fool-proofing: if it cannot parse a single issue entry it fails loudly, and never produces the fake green light of "no revisions needed". Step five, binding: review-and-revise first, render-and-deliver second is an order the script enforces; the output is one volume per subject plus an optional master volume (cover, table of contents, PDF bookmark jumps), three levels of typesetting density, error-prone and easily confused points rendered as pale-blue blocks, and a style set that is grayscale-safe — labels and hierarchy stay legible in black-and-white printing.

Several engineering floors hold all of this up: atomic JSON writes, a process lock against concurrent runs, login state kept only in a local browser profile, and anti-injection plus a write-path whitelist built into every subagent prompt. For implementation details and the full security audit, see the project page [zhuma-fakao-review](/en/projects/zhuma-fakao-review/).

## Verification

The measured scale of one complete run: 18 subjects (9 in objective Paper I + 9 in objective Paper II) and 180 chapters that hold questions; 1,655 unique wrong answers (the chapters sum to an expected 1,661; the difference is questions repeated across chapters, deduplicated by id); 41 processing units, fetched in about 9 minutes. The notes were generated by 39 subagents in five parallel batches, with 2 units written by hand by the main Agent after 429 rate limits. The final output: 18 single-subject PDFs totaling 8.3MB, plus a 129-page master volume at 4.2MB.

The pipeline's own quality has a floor too: npm test runs 22 cases covering argument parsing, atomic writes, stale-lock takeover, unit slicing and the manifest, and the fake-green-light guard (a review report with zero parsed issues must fail with exit code 2), all verified end to end as CLI runs against temporary directories; the repository also went through two rounds of independent code review plus a re-review acceptance, with the process on record in git history and the security audit document.

## Boundaries

This pipeline processes only real wrong answers from my own account: read-only toward the platform (no submitting papers, no touching answer records), serial fetching at a default 150ms interval. Wrong-answer content and the learner profile go out as prompts to the model provider in use — one of only two data channels out of this machine in the whole pipeline; the other happens only when the master PDF is copied to a desktop inside cloud-sync scope.

The output is recitation notes; do not mistake it for knowledge itself: the notes work back from wrong answers and cover the heavily tested, error-prone and easily confused knowledge points; they replace manual sorting, but solving, correcting and thinking are still yours to do. The six-dimension review is LLM-driven: the revision list can stop P0-grade issues, but that is not a guarantee of zero omissions.

Known failures are recorded honestly under "known limitations" in the project README: the API cannot return "my wrong choices" — it records which questions were missed, not the option picked at the time; it covers objective questions only — the essay-question wrong-answer book has a different structure and was not adapted; it depends on Zhuma's internal API and may break on a frontend redesign; login state expires and needs a fresh QR scan; and in the master PDF each unit's chapter numbering is independent, so numbering restarts occur, mitigated with "Part N (continued)".
