## 问题与边界

想知道时间花在了哪里，戴耳机的时间占大头，但手动打卡坚持不了。这个工具常驻托盘：插上耳机开始会话，有声音才按当前场景开段，切到无声窗口（微信、QQ）不记录不打扰。边界与口径都写在 README：记录的是默认输出设备，音箱外放若为默认端点会被算作一次会话；并发标签在场景切换时刻采样，不实时跟随；「有声时长」和「佩戴时长」是两个口径，设备页含无声、总览只算出声的，对不上是设计而非 bug。已知简化五条全部列出，误插 60 秒内自动丢弃。

## 机制

技术栈 .NET 10 加 WinForms：NAudio 监听默认输出设备变化，Core Audio COM 枚举发声进程，Win32 轮询前台窗口做场景匹配，SQLite WAL 存储并按本地日界聚合跨午夜段。跨场景切换且目标窗口正在发声才弹气泡确认（确认 / 改标 / 稍后标，3 分钟无操作自动落库），防误记靠拔除去抖与音频迟滞。统计窗四页：总览卡片加场景饼图、7×24 热力图、分耳机统计、多条件筛选明细（可编辑删除、导出 CSV）；场景规则存表，明细页可写新规则热生效。

## 验证

正确性靠 65 个 xUnit 单元测试锁住，`dotnet test` 一条命令可复跑。本地仓库 tests 目录逐文件清点：场景规则引擎 14 个、会话状态机 30 个、统计仓储与聚合 20 个、冒烟测试 1 个，合计 65，与 README 徽标「Tests 65 passing」及正文数字一致。测试刻意不碰真实硬件：音频设备与前台窗口都换成假件（假音频设备、假前台驱动），把会话状态机和规则引擎从 Windows API 里隔离出来，纯逻辑可重复执行。统计聚合的用例集中在几处容易算错的地方：并发场景的时长重叠计入、跨午夜段按本地日界拆分到各日、按设备分组；明细的编辑与删除也有用例覆盖。

## 已知失败

README 承认的简化有五条，其中影响数据的几条：气泡超时、忽略、「稍后标」一律标未确认（confirmed=0）但统计仍计入；并发标签是场景切换或声音开始那一刻的采样，听歌中途停了标签还挂着；明细默认只下发最近 3000 条；场景规则没有完整的图形化管理界面。更结构性的限制有两条。其一，只认 Windows 默认输出设备，音箱外放若是默认端点会被算成一次「耳机」会话。其二，插拔事件依赖 NAudio 经驱动上报，睡眠唤醒、驱动重置会漏事件，兜底是启动时给悬挂会话补结束时间，中间丢掉的过程补不回来，2.5 秒去抖窗口也是给驱动抖动让的步。发声判定靠每 2 秒采样一次 Core Audio 的 audio session，连续 2 次采样（约 4 秒）无声音才收段，采样间隙内的极短声音不保证成段。平台范围：Windows 11 为主，Win10 19041+ 可用但需自装 WebView2 运行时；开机自启写注册表 Run 键，前台扫描用 Win32 API，这套依赖决定了它出不了 Windows。
