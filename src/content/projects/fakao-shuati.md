## 问题与边界

主观题备考缺一个能反复练、练完立刻按采分点改的地方：市面平台题目固定，自己的错题留不下来。这个平台自托管，题库自己灌，答完一键提交 AI 按采分点判分。边界说在前面：仓库是纯工具，不含任何题目、答案、解析或采分点（著作权边界），题库数据需要用你自己在题库平台的合法账号获取；AI 判分结果只作练习参考，与真实阅卷有差异。部署上按私有服务设计：全站密码保护、noindex 响应头、worker API 随机 token，不建议无保护暴露公网。

## 机制

答题页两栏布局，题干左侧固定，每个小问独立作答框，5 秒自动保存，带考试日倒计时和模拟计时。判分按 fakao-grader 的采分点口径，AI 输出结构化分数加 Markdown 复盘：逐点对照、丢分类型分布（结论 / 依据 / 分析）、答案与作答对比。错题本从丢分采分点自动派生，重做通过即清除；背诵模块把采分点做成抽认卡，可标记掌握。统计面板给得分率、采分点命中趋势和科目覆盖进度。多账号数据隔离，适合和朋友合租一台服务器。

## 验证

正确性靠冒烟测试加结构断言：仓库带 5 条冒烟测试（npm test），README 列出的覆盖面是题库加载、认证数据链、报告采集入库、Markdown 渲染，以及一条端到端批改链路。端到端那条在本机起一个假的 OpenAI 兼容端点，走完整的 processOne 批改流程，测试断言提示词里确实装进了题干、采分点和白名单等价表述，报告的标记段能解析、缺标记段或缺字段时返回 null，最后分数入库且 Markdown 报告落盘。同一套测试跑在 GitHub Actions 的 CI（Node 22）上。要说明的是，判分准确性本身没有自动化评测：AI 打得对不对，取决于 subKeyWord 采分点数据质量和所配模型，README 把 subKeyWord 称为「批改质量的核心」，免责声明也写明结果与真实阅卷有差异。实际使用中的核验方式是三种渠道互备：API 直连、本地 CLI 加 fakao-grader 技能、报告导入页手动粘贴，任何一条路出来的报告都走同一个入库函数，可以用第三方来源的批改结果做交叉比对。

## 已知失败

- 判分主观性边界：AI 批改仅供练习参考，与真实阅卷评分存在差异（README 免责声明）；结论定性写错会触发连锁失分，这条判定好不好用，取决于采分点里 blackList 的编写质量。
- 私有自托管定位：express 单进程、SQLite WAL 单写者，不做横向扩展；服务默认监听 127.0.0.1，按朋友间共享的私人站设计，README 明确不建议无保护暴露公网，公开部署需自加反代认证。
- API 依赖：批改质量随所配模型浮动；任务失败标记 failed 后没有自动重试，靠 worker 认领或人工重试，单次批改 15 分钟超时；CLI 与 worker 模式还依赖那台机器上的 AI CLI 与技能配置。
- 数据面：gradings 表只存报告文件路径，数据目录需要整体搬移；题库文件改动即时生效、没有版本化；API Key 存在本机 SQLite 里，设置页只回显后 4 位。
