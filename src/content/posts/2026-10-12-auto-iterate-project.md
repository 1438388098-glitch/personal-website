"去把这个仓库持续优化一下。"

这种交代给 AI Agent 的宽泛任务，听起来很美好，但在工程落地时，死法通常高度一致：要么是干了十分钟就宣称"我已经看完了，没有发现明显需要修改的地方"，原地干耗到会话超时；要么是胆大妄为，不加验证地一通乱改，等第二天你睡醒打开电脑，发现整个 Git 仓库的代码早已经被改瘫痪了。

为了让 Agent 能真正稳定地通宵跑自主迭代，我写了 `auto-iterate-project`。它能在单个会话中接管 Git 仓库：摸排项目现状、挑出高价值问题、小步编码、执行验证、提交、记账，周而复始，直到达成目标或耗尽资源。

跑通这套闭环的核心，其实就是把过去踩过的四种"死法"变成硬性工程防线。

#### 死法一：原地摸鱼，声称无活可干

很多时候模型想干，只是上下文空了不知道下一步该做什么，于是一直重复执行 `git status`。

我们在调度协议上做成了三层驱动：

* **供给层（Mine）：** 内置了测试覆盖盲区、高频变更热点、未导出废弃符号、文档与实现漂移等 7 个扫描器，每次扫描都能把静态代码事实转化成具体的改进候选。Agent 迷茫时的第一个动作必须是去挖候选任务，禁止凭空瞎想。
* **指挥层（Check）：** 状态机每轮只返回明确指令（开工、挖矿、深挖扩容、停机），保证循环指针永远有确定的下一步。
* **动态配额排序：** 早期版本按"价值/工作量"排序，结果模型专门挑改拼写错误、加注释这类既便宜又无聊的杂活刷分；现在加入了期望收益评估、同类型任务限额（每轮同一类动作最多选两项）以及最低价值门槛，逼着它去碰硬骨头。

#### 死法二：改完不跑测试，盲目自信 Commit

为了防止模型一路改崩代码，流水线把验证变成了节奏呼吸：

每个候选修改必须独立成章。轮次之间只跑轻量的语法和静态类型检查（Smoke），但提交前以及收尾时，强制跑全量测试套件。一旦测试失败，优先进入原位修复流程；修复重试超过限制，本轮直接标记为阻塞；连续两次阻塞，整套自主运行直接熔断自保。

我们甚至还要提防"假绿灯"：有时候测试命令因为 Bash 管道处理不当，虽然用例挂了但最后的退出码依然是 0，导致 Agent 以为全绿了继续跑。现在的约束要求在进入循环前，必须先证明你的检查脚本在遇到坏代码时真的能报出非零错误。

#### 死法三：没有任何证据，单方面宣布"大功告成"

v1.6.0 的发布说明里记录过一次尴尬的事故：一次自主迭代在距离设定的截止时间还有 5 个小时的时候，突然抛出一句"待办事项已全部清空"，然后堂而皇之地提前收工了。

把"完成"的权利留给模型是靠不住的，必须做成代码层面的硬门禁：
只要设定的终止条件没满足、或者任务池里还有就绪候选、或者扫描器还没穷尽（连续两轮扫描零新发现才算穷尽），系统直接拒绝退出；模型声称"某某目标已完成"，必须回传对应的验证轮次号和 Diff 证据，否则一律驳回判定，不给偷懒留口子。

#### 死法四：缺乏硬性预算，死循环跑飞

在自动化守护中，没有设置退出条件的运行是绝对禁止启动的。我们从四个维度划定了边界：最大轮数、相对超时时长、Token 软预算上限，以及绝对的系统时间（比如严格卡死在"明天早上 08:00 前收工"）。

预算控制里也有不少坑。比如早期版本曾经出现过给 `--max-minutes` 传了个 `NaN`，结果浮点数判断永远成立，循环根本停不下来；深层扩容生成的子 Agent 花费如果没归集，容易把主进程的 Token 预算打穿；现在不管是时间校验、多波次封顶，还是基于单调水位的 Token 记账，都按生产级防护做了兜底。

这套工程逻辑最终经受住了自举考验：`auto-iterate-project` 的 1.6.0 版本本身，就是靠这套系统挂机跑了 20 轮通宵自迭代修改出来的。把规则焊死在流程里，AI 才能从一个靠不住的碰运气玩具，变成一个靠谱的夜间值班搭子。
