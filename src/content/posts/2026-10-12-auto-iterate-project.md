「让 AI 持续改进这个项目」这类指令只需一句委托，实际失败形态相当固定：agent 干一会儿就宣布「没发现明显可做的事」，干等截止时间；或者不验证一路改下去，把仓库改坏。auto-iterate-project 是我为这类场景写的工程化方案：在 agent 会话里自主迭代任意 git 项目，分析仓库、挑高价值改进、小步实现、验证、提交、循环，直到达标或预算耗尽；兼容 opencode、Claude Code、Codex 等 runtime（自动探测），git 是唯一外部依赖。一轮的骨架是五步：check 定停止条件与预算，mine 从仓库事实挖候选，rank 排本轮批次，implement、verify、commit 逐候选实现与验证，record 记账。

## 死法一：闲置

声称没活可干、原地等时间耗尽、反复重读仓库却不开工，在协议里是明文违规。机制分三层。供给层：mine 带七个扫描器（测试缺口、热点、死导出、文档漂移等），把仓库事实变成带证据的候选；agent 不知道做什么时，第一个动作永远是 mine，判断式的 Deep Expansion 只算第二波。指挥层：check 每轮返回 work、mine、expand、stop 之一，循环永远有下一条命令。纪律层：每个允许继续的 check 之后必须紧跟挖矿、开轮或扩容，空候选池构不成停工理由。供给之后是排序：早期按「价值除以工作量」评分，便宜杂活会系统性压过高价值工作；现在按每轮期望价值评分，附带类型多样性配额（每轮同类型至多两项）、价值下限（默认 3）、随进度收紧的风险权重，以及从历史自评分学到的校准因子。

## 死法二：不验证就改

流水线把验证焊进节奏：每个候选是独立单元，全量验证每三轮一次，提交轮与收尾前必跑；轮间只跑配置里声明的 smoke 命令，且仅限语法与类型层面，冒烟通过免不掉全量验证。失败先修复重试，超过上限该轮记为 blocked，连续两次 blocked 整个运行停下。协议也提防验证工具自身失效：测试输出经管道后退出码恒为零，轮轮「绿灯」，因此要求先证明检查脚本真能报错。每次提交前对 staged diff 做常见密钥模式扫描，扫不动的二进制按有问题处理。

## 死法三：无凭据的「完成」

1.6.0 发版说明记着一次事故：一次自主运行在截止前约五小时以「backlog exhausted」为由收工，没遇到任何阻力。修复思路是把「完成」做成代码里的门槛：finish 门禁在未达停止条件、仍有就绪候选或挖矿未穷尽时直接拒绝；穷尽有严格定义，连续两次零新发现的 mine 运行才算数，从未挖过矿的仓库谈不上穷尽。目标达成同样要凭据：goal-met 不带轮次号就标记为未验证，会扣住「全部目标达成」这条停止条件。空转也摘出预算：没有工作树变化的取消记为 aborted，不消耗轮数与 token 基数。

## 死法四：无预算跑飞

红线里有一条：没有停止条件的运行禁止启动。预算共四类：max_rounds、max_minutes（自最近活动起算的倒计时）、max_tokens（按 diff 估算的软预算）、deadline（绝对墙钟，接受 ISO、+8h 或「明早八点」写法）。预算可中途调整，checkpoint_every 指定每 N 轮暂停一次，向用户汇报并确认方向。预算自身也会坏：早期版本 init --max-minutes nan 能成功写入，此后每次 check 都判定继续；现在 NaN 与无穷大在加载时即被拒绝。还有一个隐蔽的洞：Deep Expansion 子 agent 的花销对 max_tokens 不可见，1.7.0 用 max_expansion_waves 封顶；token 记账改用单调水位线，同一批改动不再重复计费。每轮写轮次历史，每十轮出阶段报告，收尾写复盘。

这套机制经受过自己的检验：1.6.0 就是二十轮通宵自托管迭代的产物，每条修复都来自真实使用撞到的摩擦。1.7.0 的效率改造基于一次真实三十轮运行的实测：agent 单轮的成本由它读取的 JSON 体积与 helper 调用次数决定，helper 自身 0.58 秒的运行时长几乎可忽略；round-prep 把原先四条命令合并成一次调用，backlog-rank 简介输出把单轮约 18KB 的排序压到 1.2KB，所有分数不变。
