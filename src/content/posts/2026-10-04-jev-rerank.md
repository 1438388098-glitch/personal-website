## 一句话

我的法条检索底座 statute-rag，精排层一直是「把候选条文丢给大模型，让它挑 5 条提到最前」。这套做法在 100 道隔离盲写题上把 Recall@5 从 66.0% 推到 92.0%，代价是每次 3 到 4 秒，以及一段能冲到 23 秒的长尾。这轮我把裁判换成 TypeSafe 的判选模型 Jev：同样的 92.0%，头部更准，单题中位 1.3 秒，每题 0.00037 美元。

## Jev 是什么：它不写文章，只下判断

Jev 是 TypeSafe 做的第一个 System One 模型，走 OpenCode Zen 的 `POST /zen/v1/systemone`。输入是一个 `state` 加若干带类型的问题，输出是带类型的答案，只有三种：

- `choice`：单选，带覆盖全部选项的概率分布；
- `score`：0 到 3 的评分，带每个刻度的概率；
- `noul`：是或否，带概率。

它不会写一段文字再让我去解析。这一点是后面所有结论的根：精排这件事本质上要的是判别力，不需要生成能力。

计价是输入每百万 token 0.042 美元、输出免费，另有一个限时的免费档。

## 为什么它正好补上精排层缺的那块

这个项目我此前扫过 15 个算法变体，全部持平或更差：交叉编码器加深、权重重扫、融合公式、聚合方式、换更大的重排模型、第三个向量家族。诊断结论是清楚的：95 道题里 91 道的正确答案本来就在召回池内，34 道漏题里 29 道的答案就在语义前 30 名，卡住的是排序器分不清「语义近邻」与「真正答案」。

那台机器上能用的交叉编码器是 110M 参数，读条文全文不够。通用大模型读得懂，但一次要 4 千 token、3 到 4 秒。Jev 恰好落在「读得懂、只做判断、快」这一档，这是我没有的第三种选择。

## 接入方式：把排序问题改成判选问题

它不能一行替换掉原来的裁判层，因为原来的做法是让 chat 模型输出一个 JSON 序号数组，而 Jev 只给每个候选一个判断。我写了两种模式把判断转成排序：

- **choice 模式（默认）**：把 50 条候选当作一个单选问题的选项，一次调用拿回覆盖全部 50 条的概率分布，按概率降序取头部。这是最贴合重排语义的一种，一次请求就够。
- **score 模式**：给每条候选各问一个问题，各自独立打分，按分值降序取头部。

两者共用同一套契约，与原来的裁判层完全一致：只调顺序、不发明条目、任何失败原序降级、只用标准库、不进核心 import 链。前端不需要为它们写两套逻辑。

## 三张实测表

先说口径。评测用 100 道第二轮隔离盲写题，出题方看不到语料与代码，与本地管线共用同一份候选池，只差裁判。动任何结论前先校准，本机把现行管线复现到 Recall@5 66.0%、R@10 72.0%、R@30 89.0%，与仓库记录的权威数字逐位一致。

**效果。**

| 裁判 | R@5 | R@1 | 救回 / 挤掉 |
|---|---|---|---|
| 本地管线（无裁判） | 66.0% | 32.0% | 无 |
| longcat（chat，免费档） | 92.0% | 82.0% | 26 / 0 |
| DeepSeek v4.1-flash（chat） | 92.0% | 85.0% | 无 |
| **Jev choice（付费档）** | **92.0%** | **84.0%** | 26 / 0 |
| Jev score（付费档） | 92.0% | 82.0% | 26 / 0 |

92.0% 是候选深度打满的天花板：剩下 8 道的正确答案根本不在前 50 名里，属召回缺口，换任何裁判都救不了。Jev 的价值在头部：R@1 84.0% 高于 chat 裁判的 82.0%，略低于 DeepSeek 的 85% 到 86%。

**速度。**

| 裁判 | 单次 p50 | p95 |
|---|---|---|
| Jev choice | 1278 ms | 2464 ms |
| Jev score | 1332 ms | 2538 ms |
| DeepSeek v4.1-flash | 2750 ms | 无记录 |
| longcat（chat） | 3614 ms | 22984 ms |

longcat 那 23 秒的 p95 是同一批跑出来的。交互式界面上最坏那几秒比中位数更影响体感，这一点比中位数提升更有意义。

**成本。**按各自响应里回传的 token 计，单价不同不能直接比 token 数。

| 裁判 | 输入 / 输出 token 每题 | 100 题费用 |
|---|---|---|
| Jev choice | 8755 / 408 | 0.0368 美元 |
| Jev score | 11723 / 745 | 0.0492 美元 |
| DeepSeek v4.1-flash | 4242 / 13 | 套餐内，按标价折 0.0644 美元 |
| longcat（免费档） | 4176 / 15 | 0 |

Jev 的输出是概率数组，而输出这一侧不计费，所以贵的那部分全在输入上。choice 模式每题 0.00037 美元，比 DeepSeek 按标价折算还低一点。

并发我单独压测过：单个密钥从 1 并发一路加到 64 并发，零失败、零 429，单次延迟稳定在 1.2 到 1.3 秒不随并发上升，64 并发时聚合吞吐约 22.5 请求每秒。

## 诚实的短板

**免费档不能用。**当天连续跑了数百次之后，端点开始返回 429 `FreeUsageLimitError`，实测 100 次里有 62 到 100 次降级成原序返回。降级逻辑救得了可用性，救不了效果，生产必须用付费档。这一点我一开始没预料到，是压测时才撞上的。

**头部还差 DeepSeek 一点。**84.0% 对 85% 到 86%，在 ±2 题的单次抖动范围内，但方向是真的。

**概率是相对量。**choice 模式的概率受同批候选影响，换一批候选同一条文的概率就变了，所以不能拿它设绝对阈值。要做「低于 X 分就判定没检到」这种拒答逻辑，得用 score 模式拿绝对刻度，或者单独用 `noul` 问一句。

**天花板还是召回。**这次换裁判没有、也不可能动那 8 道召回缺口。

## 对法律科技的启发

第一，判选模型把精排层从「调一次大模型 API」变成「调一个便宜的专用接口」。个人律师与小所不会为一次检索付一厘钱，但会因为等 3 秒而放弃；两者同时解决，这层改造才值得做。

第二，把判分显示出来比藏起来更有用。界面上每条结果带一个「Jev 判分 0.93」和一条细条，悬停还能看到这题的判选置信度与消耗的 token。法律场景里用户对黑箱格外警惕，一个能看懂、能质疑的数字，比一段流畅的说辞更能建立信任。

第三，选裁判前先量瓶颈。这轮如果我继续去调融合权重，就是又一次白费。15 个变体全部无效加上「91/95 的答案已在池内」这个诊断，才让「换判别器」这条路径浮出来。

## 复现

代码与完整实测记录在 github.com/1438388098-glitch/statute-rag，报告在仓库的 `docs/retrieval-jev-rerank.md`。核心命令：

```bash
# 三路并列评测（本地管线 + Jev + chat 裁判），首跑把候选池落盘
STATUTE_RAG_JEV_KEY=... STATUTE_RAG_JEV_MODEL=jev-1.13 \
  py -3.13 scripts/eval_jev_rerank.py --workers 5 \
    --pools data/flk/tmp/pools --tag paid_choice

# 在线演示（精排裁判默认优先 Jev）
py -3.13 scripts/app.py --corpus data/corpus_v7.jsonl
```

单测 19 例新增，全部不联网：契约、两种模式、失败降级、并列稳定性、环境变量配置，以及接口层展示判分的用例。
